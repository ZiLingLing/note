# System Considerations
## 第二十七章 程序规模对构建的影响
随着程序规模的增大， 工作量增加和程序规模之间并非线性关系，工作量增加得会越来越多（画成工作量为y程序规模为x函数就是斜率越来越大）。同样的，大项目和小项目之间的方法、策略也不互通。
### 27.1 交流和规模
开发组内部每两人之间算作一条“交流路径”时，随着参与项目的成员数目增加，交流路径也会随之增加，两者关系是乘性的，交流路径的条数大致正比于人数的平方。也就是在大项目中必须采取一些组织技术来改善交流效率，或者有意地对其加以限制。常用方法是采用正式的文档。

### 27.2 项目规模的范围
项目规模的范围很宽，这意味着不能把任何一种规模视为典型。评估项目规模的方法之一是考虑项目团队的规模。对于项目团队规模，可能还需要知道项目人员中程序员的比例。

### 27.3 项目规模对错误的影响
项目的规模既会影响错误的数量，也会影响错误的类型。对于小项目，构建错误占大部分，随着项目规模的增大，通常更大一部分错误要归咎于需求和设计。

### 27.4 项目规模对生产率的影响
在与项目规模的关系方面，生产率的情况与软件质量相似。对于小项目（2000行代码或更少），影响生产率最大的原因是单个程序员的技巧。随着项目规模和团队规模的增大，组织方式对生产率的影响也将随之增大。

### 27.5 项目规模对开发活动的影响
人数越少个人的影响因素越大，人越多组织结构对项目成败影响力更大。
- 活动比例和项目规模  
  对于中型小型项目，构建是最主要的活动。随着项目规模增长，虽然构建活动的时间增加了，但类似于交流、计划、管理部分花费的时间增长得更快，超越了线性。P655列举了一些增长更快的活动。  
  
- 程序、产品、系统和系统产品  
  代码行数和团队规模并不是影响项目大小仅有的因素。另一个更敏感的原因是最终软件的质量和复杂度。  
  
- 方法论和规模
  对于小项目，方法论的应用显得很不经意且趋于本能；对于大项目，它们的应用变得很严格，并且计划得十分仔细。项目越正规条条框框也就越多，但对于方法论并非越多越好，就像敏捷和计划驱动相比，敏捷作为小的方法论，应用时逐渐扩充为适用于大项目效果强于计划驱动这种一开始就囊括一切的方法论。主要还是考虑项目的实际规模和类型，选择适量级的方法论。

## 第二十八章 管理构建
### 28.1 鼓励良好的编码实践
代码是构建活动最主要的产出，因此管理构建中的一个关键问题就是“如何鼓励良好的编码实践”。从管理的角度出发，采取一套严格的技术标准并不是个好主意，制定标准应当由一位受人尊敬的架构师（不是长期不再接触编码的资深闲散人员）来做而不应该由管理者来做。
- 设定标准的考虑事项  
  对不同的组织有不同的标准，或严格或灵活主要看项目内程序员们的喜好。  
  
- 鼓励良好的编码实践技术  
  编码实践比呆板的编码标准更容易执行。下面有一些良好的编码实践：
  - 给一个项目的每一部分分派两个人  
    这样做起码有两个人认为代码是可工作且可读的。包括前文提过的结对编程、导师带学生、复审、伙伴系统（各负责另一个人之安全的两人同行制）。
  - 逐行复查代码
  - 要求代码签名
  - 安排一些好的代码供人参考
  - 强调代码是公有财产  
    代码要对所有人公开，至少要在代码复查的时候公开。
  - 奖励好代码  
    运用奖励机制来激励良好的代码实践。
  - 一份简单的标准  
    如果有编程背景，宣称“我必须能读懂你项目里的所有代码”，在管理者不是技术尖子时反而有助于产生看似聪明但是难以理解的代码。

### 28.2 配置管理
- 什么是配置管理  
  配置管理（变更控制）是“系统化地定义项目工件和处理变化，以使项目一直保证完整性”的实践活动。其中的技术包括评估所提交的更改、追踪更改、保留系统在不同时间点的各历史版本。  
  
  如果不对需求变更加以控制，就可能为系统中最终会去除的部件编写代码，也会写一些可能与系统中新的部件不兼容的代码。也可能会修改别人正在修改的子程序，此时合并上会出问题，会导致测试时的版本已经落后，这样就是旧版本也没有测试到，新版本也没有进行测试，并且发现新的错误时无法恢复到最初可以工作的旧版本了。  
  
- 需求变更和设计变更  
  控制设计变更的指导原则：  
  - 遵循某种系统化的变更控制手续
  - 成组的处理变更请求  
    记下所有的想法和建议，不管它实现起来有多容易。记录下来直到有时间去处理它们，到时候把它们当作一个整体看待，从其中选取最有益的一些变更来实施。
  - 评估每项的变更成本
  - 提防大量的变更请求
  - 成立变更控制委员会等机构  
    其职责是在收到变更请求时去芜存精。
  - 警惕官僚主义，但也不要因为害怕官僚主义而排斥有效的变更控制  
  
- 软件代码变更  
  配置管理的另一项是源代码控制，常常需要通过比对旧版本甚至更早版本的代码来查找错误的线索，这个时候使用版本控制工具就格外重要。版本控制对于团队项目来说必不可少。  
  
- 工具版本  
  对于某些种类的项目而言，需要拥有构造出“创建软件各个特定版本”的原样环境的能力。此时编译器、链接器、代码库等这些工具也需要纳入版本控制。  

- 机器配置  
  采用标准化配置有助于避免“配置不同”或者“使用工具的版本不同”等等原因造成的麻烦。为标准的开发工作站生成一份磁盘映像，然后将文件加载到每位开发者的机器上，这也极大简化了机器的安装过程。  
  
- 备份计划  
  定期备份工作。这样能避免磁盘损坏、误删文件、机器损坏等等突发情况带来的损失。不仅仅备份代码，还包括文档、图表、笔记等。同时要记得测试备份，确保它包含所有数据并且可以成功地恢复。

### 28.3 评估构建进度表
- 评估的方法  
  可以采用下列一种或几种方法评估项目规模和完成它需要的工作量：
  - 使用评估软件
  - 使用算法方法，也就是评估模型
  - 聘请外界的评估专家来评估有关项目
  - 为评估举行排练会议（不是很理解，书上也没有给出解释）
  - 评估项目的每一部分，然后把它们加起来
  - 让成员评估各自的任务，然后再把各任务的评估值加起来
  - 参考以往的项目经验
  - 保留以往的项目评估，查看其准确度，用它来调整新的评估  
  
  下面是一套评估项目的好方法：
  - 建立目标
    建立一个准确的目标，清楚评估的具体对象、清楚评估的准确度。书P671给出了一些评估的思路。
  - 为评估留出时间，并且做出计划
  - 清楚地说明软件需求
  - 在底层细节层面进行评估
  - 使用若干种不同的评估方法，并且比较其结果
  - 定期做重新评估  
  
- 评估构建的工作量  
  构建所占比例随着项目规模的不同而变化。把你的组织的项目经验记录下来，然后用它评估未来项目需要花费的时间。
  
- 对进度的影响  
  对项目进度影响最大的是所开发程序的规模。但除此以外还有很多其他的因素也会对软件开发造成影响。书上P674有详细图表已将部分影响因素的影响效果做了量化。  
  以下是一些能影响开发进度但不易被量化的因素：
  - 需求开发者的经验和能力
  - 程序员的经验和能力
  - 团队的动力
  - 管理的质量
  - 重用的代码数量
  - 人员流动性
  - 需求变更
  - 客户关系的质量
  - 用户对需求的参与度
  - 客户对此类应用软件的经验
  - 程序员对需求开发的参与程度
  - 计算机、程序和数据的分级安全环境
  - 文档量
  - 项目目标（进度、质量、可用性以及其他可能目标）  
  
- 评估与控制  
  在控制人员和技术资源开销的角度上来说，最初评估的准确度的重要性远远比不上“随后为了完成进度而成功控制资源”的重要性。  
  
- 如果你落后了该怎么办  
  项目平均会超出原定完成时间的100%，当落后的时候，如果增加时间可行就那么做，如果不可行（通常情况下），可以采取下面的一种或几种方案：
  - 希望自己能赶上  
    持乐观态度，如果需求所花的时间比预期长，那么就希望在后期编码和测试时把时间补回来。越接近项目后期延误和超支的现象就越严重。项目并不能在后期把时间补回来：而是会越来越落后。
  - 扩充团队  
    有时扩充团队会使得情况变得更糟，使得项目进度推进变得更慢，因此需要分割项目，把适合的部分交给后期才加入进来的人。
  - 缩减项目范围

### 28.4 度量
