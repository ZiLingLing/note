# Code Improvement
## 第二十章 软件质量概述
### 20.1 软件质量的特性
软件同时拥有外在和内在的质量特性，  
  
外在特性指该产品的用户所能感受到的部分，是用户关心的唯一特性，用户不必关心任何内在的实现，只需要关心是否可用是否易用。包括以下内容（有一部分相互重叠，但有不同含有，且在不同场合下重要性也有所不同）：
- 正确性  
  指系统规范、设计和实现方面的错误稀少程度。
- 可用性  
  指用户学习和使用一个系统的容易程度。
- 效率  
  指软件是否尽可能少地占用系统资源，包括内存和运行时间。
- 可靠性  
  指在指定的必需条件下，一个系统完成所需要功能的能力——应该有很长的平均无故障时间。
- 完整性  
  指系统阻止对程序或者数据进行未经验证或者不正确访问的能力。这里的完整性除了包括限制未经授权用户访问以外，还包括确保数据能够正确访问。
- 适应性  
  指为特定的应用或者环境设计的系统，在不做修改的情况下，能够在其他应用或者环境中使用的范围。
- 精确性  
  指对于一个已经开发出的系统，输出结果的误差程度，尤其在输出的是数量值的时候。
- 健壮性  
  指系统在接收无效输入或者处于压力环境时继续正常运行的能力。
  
程序员除了关心软件质量的外在特性之外，还要关心它的内在特性：
- 可维护性  
  指是否能够很容易对系统进行修改、改变或者增加功能，提高性能，以及修正缺陷。
- 灵活性  
  指假如一个系统是为特定用途或者环境而设计的，那么当该系统被用于其他目的或者环境的时候，需要对系统做修改的程度。
- 可移植性  
  指为了在原来设计的特定环境之外运行，对系统做修改的难易程度。
- 可重用性  
  指系统的某些部分可被应用到其他系统中的程度，以及此项工作的难易程度。
- 可读性  
  指阅读并理解系统代码的难易程度，尤其是在细节语句的层次上。
- 可测试性  
  指的是你可以进行何种程度的单元测试或者系统测试，以及在何种程度上验证系统是否符合需求。
- 可理解性  
  指在系统组织和细节语句层次上理解整个系统的难易程度。与可读性相比，可理解性对系统提出了更高的内在一致性要求。
  
书P466给出了一些质量特性之间的典型关系，对于质量特性之间的关系的叙述和总结在书P465
  
### 20.2 改善软件质量的技术
虽然开发一个高质量产品最好的方法似乎就是专注于产品本身，但就软件质量保证而言，还需要关心开发过程。
  - 软件质量目标  
    根据前文提到的外在和内在特性，明确定义出软件质量的目标。如果没有一个明确的目标，那么程序员去极力增强的特性就可能与你所强调的特性有别。
  - 明确定义质量保证工作  
    在质量保证工作中，一个最常见的问题是质量被认为是次要目标。组织必须向程序员说明，质量应当放在第一位。将质量保证工作明确下来，可以清楚表达这件事情的优先程度，程序员就会据此做出响应。
  - 测试策略  
    执行测试可以为产品的可靠性进行详细的评估。
  - 软件工程指南  
    在开发过程中，指南应当控制软件的技术特性，它应当贯彻到所有开发活动中去，包括定义、需求分析、架构设计、构建以及系统测试。
  - 非正式技术复查  
    开发人员在正式复查前自行检查工作。包括对设计或代码的桌面检查或者和若干同事一起代码走查一遍。  
    PS：1.桌面检查：开发人员自己进行的代码缺陷检测方法。开发人员通过阅读程序、对照错误列表、推演测试数据等方式对所编写的代码进行缺陷检测。  
        2.代码走查：开发人员与架构师集中讨论代码的过程，旨在交换有关代码书写的思路，并建立一个对代码的标准集体阐述。
  - 正式技术复查  
    为了在低成本（投资最小并且修正问题成本最小）的环境里抓出问题。周期性检验产品是否已经具备了进入下一阶段前所要求的质量。
  - 外部审查  
    是一种用于确定一个已开发项目或产品的特殊技术复查方法。一个审查小组由开发组织以外的人员构成，并向委托人汇报审查结果。
  
- 开发过程
  - 对变更进行控制的过程  
    实现软件质量目标的拦路虎之一就是失控的变更。有效地管理变更是实现高质量的一个关键。
  - 结果的量化  
    除非质量保证计划的结果经过实际测量，否则你将完全不知道这个计划是否有实效。量化结果能告诉你计划成功与否，并且允许你用可控的方式来调整你的计划，去看你如何改善它。
  - 制作原型  
    制作原型是指开发出系统中关键功能的实际模型。
  
- 设置目标  
  明确设置目标是开发高质量软件的一个简单而清晰的步骤，但它经常被忽略。程序员无法对一堆天天都在改变，或者无法实现的目标做出反映。
  
  本书P469的表格是“设置质量工作目标（的类型）对于程序员工作表现影响”的实验结果。
  
### 20.3 不同质量保证技术的相对效能
- 缺陷检测率  
  P470展示几种常见的缺陷检测技术的缺陷检测率。

  如果项目的开发者要向更高的缺陷检测率发起冲击，需要综合运用各种技术。
- 找出缺陷的成本  
  检查（非正式技术复查）比测试的成本更小。
- 修正缺陷的成本  
  一个缺陷存在时间越长，修复成本越高；一步到位的修正方法（例如代码复查）修正缺陷的成本低于两步走的方法（例如测试）。

  通过下面方法这一方法推荐阵容，可以获取高于平均水平的质量：
  - 对所有的需求、架构以及系统关键部分的设计进行正式复查
  - 建模或者创建原型
  - 代码阅读或者检查
  - 执行测试

### 20.4 什么时候进行质量保证工作
错误越早引入到软件中问题就会越复杂，修正这个错误的成本也就越高。缺陷可能在任何阶段渗透到软件中，因此，需要在早期阶段就开始强调质量保证工作，并且将其贯彻到项目的余下部分中。

### 20.5 软件质量的普遍原理
软件质量的普遍原理就是改善质量以降低开发成本。

## 第二十一章 协同构建
### 21.1 协同开发实践概要
“协同编程”包括结对编程、正式检查、非正式技术复查、文档阅读，以及其他让开发人员共同承担创建代码及其他工作产品责任的技术。
- 协同构建是其他质量保证技术的补充
  在20章末尾的一节里提到过“软件测试在单独运用的时候效果比较有限”，对缺陷的检出率平均在30%到40%之间，对设计和代码的检查平均效能在55%到60%。正因为有限的检测效果，显而易见的是协同构建一是能提高检测效能，二是能缩短开发周期降低开发成本。  
  结对编程的代码质量能达到与正式检查相近的水准，对代码检查来说并无优势，但是在成本只比单人开发高约10%到25%的情况下开发周期缩短45%。  
  书P481给出一些例子来说明技术性复查能大幅缩短开发周期。在减少软件中的缺陷数量时缩短了开发周期。
- 协同构建有利于传授公司文化以及专业编程知识  
  程序员需要得到程序设计方面的主观反馈，复查为资深程序员传授给刚出道的程序员知识提供了一个平台、一个契机，这是培养新人的好机会。复查可以快速地将所有开发者的水平提升到最优秀开发者的高度。
- 集体所有权适用于所用形式的协同构建  
  在集体所有权下，所有代码都属于团队而不是某一个人，并且团队中的所有成员都可以对它进行访问和修改，带来的好处如下：  
  - 众多双眼睛的检查，以及众多程序员的合力编写，可以使代码质量变得更高。
  - 某个人离开项目所造成的影响更小了，因为每一段代码都有多个人熟悉它。
  - 总体上缺陷修正的周期变短了。
- 在构建前后都应保持协作  
  协同构建的思想同样适用于评估、计划、需求、架构、测试以及维护工作等阶段。

### 21.2 结对编程
- 成功运用结对编程的关键
  需要遵循下面几条准则：
  - 用编码规范来支持结对编程
  - 不要让结对编程变成旁观  
    不掌握键盘的人应该主动参与到变成中，提前思考
  - 不要强迫在简单的问题上使用结对编程
  - 有规律地对结对人员和分配的工作任务进行轮换  
    结对编程的好处在于能够让不同的人熟悉系统的不同部分。有规律地轮换有助于知识传播。
  - 鼓励双方跟上对方的步伐
  - 确认两个人都能看到显示器  
    实际上我觉得应该是确保两个人都能看清楚代码写的什么。
  - 不要强迫程序员与自己关系紧张的人组对
  - 避免新手组合
  - 指定一个组长  
    指定一个人来协调工作的分配，对结果负责以及负责与项目外其他人的联系。

- 结对编程的好处
  - 与单独开发相比，结对能够使人们在压力之下保持更好的状态。鼓励双方保持代码的质量，即使出现了让人不得不飞快地编写代码的压力时也是如此。
  - 能够改善代码质量。
  - 它能缩短进度时间表，结对往往能够更快地编写代码，代码的错误更少。
  - 还具有协同构建的其他好处，包括传播公司文化，指导初级程序员，培养集体归属感。

### 21.3 正式检查
详查（正式检查）是一种特殊的复查，它在侦测缺陷方面特别有效，并且相对测试来说更加经济合理。  
  
虽然任何复查的都涉及了阅读设计或者代码，但是详查还是在几个关键问题上与普通复查有所区别：
  - 详查表关注的是复查者过去所遇到的问题
  - 详查专注于缺陷的检测，而非修正
  - 复查人员要为详查会议做好预先准备，并且带来一份他们所发现的已知问题列表
  - 参与者都被赋予了明确的角色
  - 详查的主持人不是被检查产品的作者
  - 详查的主持人应该已经接受过主持详查会议方面的培训
  - 只有在与会者都做好充分准备之后才会召开详查会议
  - 每次详查所收集的数据都会被应用到以后的详查中，以便对详查进行改进
  - 高层管理人员不参加详查会议。除非正在详查一个项目的计划，或者其他管理方面的的资料。但技术负责人可能参加。

- 你期望详查能带来什么结果
  独立的详查通常能捕捉到60%的缺陷。  
  
  设计和代码联合详查通常能够去除产品中70%到85%甚至更多缺陷。详查能够在早期识别出容易产生错误的类。通过参加详查，设计师和程序员们学会了如何改善自己的工作，而详查也让生产效率提高了20%左右。  
  
  详查还可以用来评估进度，不过评估的只是技术层面的进度。这代表回答了两个问题：技术层面的工作是否已经完成？以及技术层面的工作是否完成良好？这两个问题的答案都是正式检查的副产品。  

- 详查中的人员角色  
  PS：一般来说在6个人左右，最少不要少于三个，要保证独立的主持人、作者和评论员。
  - 主持人  
    负责保证详查以特定的速度进行，使其既能保持效率，又能发现尽可能多的错误。主持人在技术上面必须能够胜任，必须能够理解项目有关的细节。这个人负责管理详查的其他方面，例如分派复查设计和代码的任务，分发详查所需的核对表，组织会议，报告详查结果，以及负责跟踪详查会议上指派的任务。
  - 作者  
    直接参与设计或者代码的人，在详查中扮演相对次要的角色。详查的目标之一就是让设计或者代码本身能够表达自己。责任是解释设计和代码中不清晰的部分，偶尔还要解释看起来有错的位置为什么实际上是可以接受的。
  - 评论员  
    同设计和代码有直接关系，但又不是作者的人。职责是找出设计和代码的缺陷。
  - 记录员  
    将详查会议期间发现的错误，以及指派的任务记录下来。作者和主持人都不该担任记录员。
  - 经理  
    在详查的时候让经理参与通常不是一个好主意，因为详查是一个纯技术性的复查。经理的出席会对交流产生影响。关注的焦点会从技术问题转移到行政问题上。不过经理有权知道详查的结果，应当准备一份详查报告让他了解情况。
  
- 详查的一般步骤
  - 计划  
    作者将设计或者代码交给主持人，主持人决定哪些人复查这些材料，并组织会议，分发核对表。
  - 概述  
    当评论员不熟悉所要详查的目标时，作者花一些时间描述这些设计或者代码的技术背景。加入概述也许有风险，因为往往会导致被检查的设计和代码中不清晰的地方被掩饰。
  - 准备  
    每一个评论员独立地对设计或者代码进行详查，找出其中的错误，评论员使用核对表来指导他们对材料的详查。当每一个评论员被赋予某一特定的视角时，详查会更有效。或者对每一个评论员赋予一个以上的待详查场景。
  - 详查会议  
    主持人挑选出除作者之外的某个人来阐述设计或者阅读代码。所有逻辑都应该被解释。保持会议适当的节奏，和适当的时间，通常不超过2小时，一天不建议安排超过一个详查会议。
  - 详查报告  
    详查会议之后主持人要写出一份详查报告，列出每一个缺陷，包括类型和严重级别。
  - 返工  
    主持人将缺陷分配给某人修复（通常是作者）。得到任务的人负责修复列表中的每个缺陷。
  - 跟进  
    主持人负责监督在详查过程中分配的返工任务。根据发现错误的数量以及严重程度选择适当的跟踪工作进展的方式。
  - 第三个小时的会议  
    这个会议允许有参与兴趣的人在正式检查结束后讨论解决方案。

- 对详查进行细调  
  略，总之就是详查中经验性的东西，书P489。

- 详查中的自尊心  
  进行详查的目的是发现设计和代码的缺陷，而不是探索替代方案或者争论对错，其目的不应该是批评作者的设计和代码。作者也应承认每一个缺陷然后继续详查，承认批评内容也不代表认同。作者负责处理缺陷，评论员也必须尊重作者如何解决某个错误的最终权力。

- 详查和《代码大全》  
  略  
  
- 详查总结  
  用于详查的核对表有助于集中注意力。由于详查有标准的核对表和标准的角色，因此它是一个系统化的过程。它是可以自我优化的，因为它采用一个正式的反馈循环来改进核对表，并跟踪准备和详查的速度。在这种全程控制和持续优化的努力下，无论一开始状况如何，详查很快就能成为一种非常强大的技术。

- 走查  
  是一种很流行的复查方式，这个词的定义很随意，其流行在于在某种程度上，人们把任何形式的复查都称为“走查”。
- 代码阅读  
  侧重于阅读代码而轻会议这种形式，直接阅读代码找出错误，同时从质量的角度对代码做出评价，例如代码设计、风格、可读性、可维护性以及效率等。（Code Review）

  通常是管理层的复查，而不是技术复查。

## 第二十二章 开发者测试

### 22.1 开发者测试在软件质量中的角色
