# Software Craftsmanship
## 第三十一章 布局与风格
本章转向计算机编程的美学话题——程序源代码的布局。编排出色的代码会带来视觉和思维上的愉悦。本章介绍的技巧不影响任何的程序性能，但会让你在日后理解代码、检查代码以及修改代码变得更容易，同时使得其他人在你缺位时更容易阅读、理解和修改你的代码。
### 31.1 基本原则
本节阐述好的布局的原理
- 布局的极端情况  
  书上P730-P732给出三个例子。第一个例子是所有代码紧密排布，但是注释完备；第二个例子有分行无缩进，无分块，也没什么有用注释；第三个例子是正常代码的例子。前面两个例子展示的代码都很烂，只不过第一个例子是“极端差”。  
  
- 格式化的基本原理  
  格式化的基本原理指出，好的布局凸显程序的逻辑结构。使代码看起来有条理的最大意义莫过于展示代码结构。如果同时有两种展示代码的方式，第一种能够更好地展示代码结构，第二种使得代码更悦目，那么理应选择第一种，而且着重逻辑表现通常不会做出难看的代码（除非代码逻辑原本就丑陋）。  
  
- 人和计算机对程序的解读  
  布局是关于程序结构的有用暗示。  
    
  计算机可能只关心花括号或者begin/end；但人看程序的时总倾向于从代码的视觉外观获取提示。书P732给出一个例子，这个例子通过缩进证明了前面的观点，for循环的语句块没有使用花括号去限定其位置，因此for循环只会执行后面跟的第一行代码，然而这行代码和接下来的两行代码的缩进相同（且语义连续，看起来确实是需要被一起执行的代码），因此第一眼看上去就像for循环语句块里有三行代码一样。  
  
- 好布局有什么用  
  编程工作量的一小部分是让机器读的程序，大部分工作是写让他人（或者过段时间之后的自己）看懂的程序。如果语句按照有意义的方式布局，有助于去感知、理解和记住程序的重要特性。  
  
- 把布局作为一种信仰  
  在实践方面应当头脑开放，接受已证实为更好的布局方法，即使调整适应过程最初会感觉有些不舒服。
  
- 良好布局的目标  
  - 准确表现代码的逻辑结构  
    好的布局主要是为了展现代码的逻辑结构，一个典型的例子，程序员利用缩进等空白来表达逻辑关系。
  - 始终如一地表现代码结构  
    有些布局风格的规则会遇到许多例外，以至很难遵守。好的风格能够适应大多数情况。
  - 改善可读性
    如果有一种缩进策略合乎逻辑却令程序更难看懂，那么它就毫无用处。好的布局方案就该增强代码的可读性。
    ```个人理解
    前文提到过的“如果同时有两种展示代码的方式，第一种能够更好地展示代码结构，第二种使得代码更悦目，那么理应选择第一种”，与这条并不冲突。我认为区别在于“悦目”并不完全等于“好的可读性”，举个例子，一段精悍凝练强大的算法，改善了的性能却往往会使代码变得难以理解。
    ```
  - 经得起修改
PS：采用不同的目标衡量这些准则，得到的结论或许不同。假设你希望将程序上代码的行数达到最少的场景中（可能是因为计算机屏幕比较小），你就会批评那些需要额外再用两行来放子程序的风格。

### 31.2 布局技术
- 空白  
  空白能够增强可读性。空白包括空格、制表符、换行、空行，是展现程序结构的主要手段。
  - 分组  
    从另一个角度看，空白也是分组，也是确保相关的语句放在一起。一段代码只应由完成某任务的语句组成，这些语句彼此相关。
  - 空行  
    将不相关的代码也很有必要。代码中的一个段落的前面应该加入空行。空行是指示一个程序如何组织的手段，可以用空行将相关语句各自划分成段落、分开子程序、突出注释部分。
  - 缩进  
    用缩进形式表示程序的逻辑结构。作为一项守则，那些逻辑上隶属于某语句的语句都应缩进。对程序的逻辑结构强调不足和过度强调都不合适，有研究表明，2到4个空格的缩进是最恰当的。  
  
- 括号  
  在运算中，把一些多项式计算中非必须括号的位置也放上括号，这样会使得运算顺序更容易理解。

### 31.3 布局风格
多数布局问题都涉及到块结构——跟在控制语句后面的那些语句组。块结构被花括号或关键字括起来（例如begin-end）。  
- 纯块结构
  许多关于布局的争论源于许多常用语言的内在缺陷。一个设计精良的语言的块结构非常清晰，适用于一种自然而然的缩进风格，如果控制结构必须有成对的开始符和结束符，代码分块是自然而然的。很多缩进问题之所以存在，就是因为得去弥补语言结构的不良设计，源于有些语言不要求块结构，例如可以在控制结构（for、if等）后只跟一条语句，而不必有正规的块，控制结构不会自动产生代码块。后面几节描述了若干种补救的方法。  
  纯块状结构表现形式：拥有开始符（{或者begin等）和结束符（}或end等），把它们视为控制语句的一部分，然后处于语句块内的语句缩进一次。在书上P739。  
  
- 模仿纯块状结构
  如果语言不支持纯块结构，可以用关键字开始符和结束符看成所在控制结构的扩展。在此类语言中，人为地将开始符和结束符分别放在控制结构内部语句的第一条语句前和最后一条语句后并且将内部语句进行缩进，以达成和纯块结构相同的布局。  
  
- 使用begin-end对（花括号）指定块边界  
  与纯块结构不同，它把开始符和结束符视为子句的一部分，因此它们也要和子句一同缩进处于同一层级。例子在P742。  
  
- 行尾布局  
  代码缩进至行的中间或者末尾。行尾缩进用于将代码块与开始它的关键字对齐，使子程序的其余参数与第一个参数对齐，或者在case语句中将各种情况对齐等类似目的，布局的例子在P743-P744。  
  
- 哪种风格最优  
  所有风格都不绝对可靠，都偶尔需要进行“合理而明显”的折中。

### 31.4 控制结构的布局
有些程序元素的布局主要牵涉美观问题，然而控制结构的布局却会影响可读性和可理解性，故而在实践中应优先考虑之。
- 格式化控制结构块的要点  
  - 不要用未缩进的begin-end对  
    例子在书上P746。因为开始和终止这样既不是控制结构的一部分，也不是其后语句的一部分。（虽然但是，现在的IDE会自动地这么做，我不清楚在现在哪种方式更对）
  - 别让begin-end两次缩进  
    例子在书P746  
  
- 其他考虑  
  下面是除了缩进之外的指导原则：
  - 段落之间要空行  
    有些代码块没有用begin-end对界定。逻辑代码块应该像一个段落一样被对待，用空行将它们各自分开。
  - 单语句代码块的格式要前后统一
  - 对于复杂表达式，将条件分隔放在几行上  
    例子在书上P749-P750。就是前文针对的复杂表达式那样，把每个单独的表达式作为一行。
  - 不用goto
    goto之间的代码布局不好办，无法确定缩进的规则。
  - case语句的布局不要有行尾布局的例外（case语句全部用行尾布局）
 
### 31.5 单条语句的布局
本节说明在程序中改善单条语句布局的多种方法。
- 语句长度  
  语句长度应限制在80个字符以内。理由如下：
  - 超过80个字符的语句很难读
  - 80个字符的限制不鼓励深度嵌套
  - 80个字符可能超过一个屏幕的宽度（但是按照当今的屏幕宽度来看这不是个问题）  
   
- 用空格使语句显得清楚  
  在语句中加入空格可以提高可读性。
  - 使用空格会让逻辑表达式更难读  
    用空格来分隔标识符，对比的例子在P753。
  - 使用空格让数组引用更容易读  
    数组下标前后加上空格。对比的例子在P754。
  - 使用空格让子程序参数更容易读  
    子程序的参数列表中的参数前使用空格，对比的例子在P754。  
  
- 格式化后续行
  此处讨论如何将较长语句延续到下一行。
  - 使续行明显  
    让第一行部分做成若其单独存在时就有明显语法错误的例子，另一个方法是将后续的字符置于后续行的开头。然后后续行相比于第一行多缩进一次。 例子在书上P754-P755。
  - 把紧密关联的元素放在一起  
    应将属于一体的东西放在一起，例如数组下标、子程序参数等。类似这样的东西放在一起。例子在书上P755-P756。
  - 将子程序调用的后续行按标准量缩进  
    也就是”后续行相比于第一行多缩进一次“，这次缩进要和代码中的其他地方的缩进量保持一致。或者让后续子程序的调用参数对齐子程序的首个参数处。
  - 让续行的结尾易于发现  
    当方法参数过多导致语句过长时，可以让每个参数占一行，以参数后的逗号结尾，最后一个参数以")"或者");"结尾（后者是函数声明时的情况）。
  - 将控制语句的后续行缩进以标准的空格数  
    也就是”后续行相比于第一行多缩进一次“
  - 不要将赋值语句按等号对齐
    因为当变量名改变，或者运行将制表符改为空格和以空格换作制表符的工具时，要继续维持等号对齐就会很麻烦。  
  
- 每行仅写一条语句  
  将多个语句放在一行的理由：这样可以少占据屏幕或者打印纸张篇幅，从而一次性能多看些代码；它也能将相关语句集中在一起，有些程序员还觉得能为编译器提供优化线索。（看起来很有道理，但是还是不如一行只写一条语句）  
  
  每行只写一条语句的理由：
  - 将每个语句单独置于一行，能够提供有关程序复杂性的准确观点。不会因为使复杂的语句看起来简单而隐藏了程序的复杂性。
  - 对于现代编译器，将多个语句放在同一行不能提供任何的优化线索。
  - 各语句占一行，代码只需自上而下读，而不用考虑多语句在同一行时额外需要的从左向右读不同语句的情况。
  - 各语句占一行，在编译器以行号指出某行有错误时，将更容易找到语法错误。
  - 各语句单独占一行，在基于行的调试器中就更容易单步地执行代码
  ```个人理解
  这个是真的亲身感受到了。
  ```
  - 各语句单独占一行，编辑单个语句会更加容易——删除一行或者临时将某行改为注释。
  ```个人理解
  这个也是深有体会。
  ```  
  
  C++中，不要让一行里有多个操作，这会带来副作用（略，书P759-P761）。  
  
- 数据声明的布局
  - 每行只声明一个数据
  - 变量声明应尽量接近其首次使用的位置
  - 合理组织声明顺序  
    按声明类型分组，无论按首字母顺序也好，还是按功能也好，还是按类型也好，总之要有分组。
  - C++中，声明指针变量时请把星号靠近变量名，或者是去声明指针类型  
    对于前者，如果不这么做，当一行里声明多个变量时，星号只会作用于第一个变量。

### 31.7 类的布局
- 类接口的布局  
  在布局类接口时，一般应按类成员按如下顺序表示：
  1.说明参数及其完整用法的头部注释  
  2.构造函数和析构函数  
  3.public子程序  
  4.protected子程序  
  5.private子程序  
  
- 类实现的布局  
  类实现通常应按以下顺序排布：  
  1.描述类所在文件之内容的头部注释  
  2.类数据  
  3.public子程序  
  4.protected子程序  
  5.private子程序  
  
  如果文件包含多个类，要清楚地标注每一个类。例子在P769。  
  
  不要过度注释，反例和正例分别在P770和P771。  
  
- 文件和程序布局
  - 一个文件应只有一个类
  - 文件的命名应与类名有关
  - 在文件中清晰地分隔各个子程序
  - 按字母顺序排列子程序
    作为“为子程序在文件中（我个人理解是按功能分组）分组”的替代方案。  
  
  对于C++，请仔细组织文件中内容的次序，C++源文件的内容的典型顺序在P773。

## 第三十二章 自说明代码
软件文档有多种形式，本章在综述文档的有关情况后，将专注于文档的特殊补充，即“注释”。
### 32.1 外部文档
软件项目的文档涵盖了源码清单内外的各种信息——常见的形式有独立的文件或者单元开发文件夹。对于大型正规项目，多数文档位于源码之外。外部结构文档通常比编码的层次更高，但比问题定义、需求和架构活动的层次低一点。
- 单元开发文件夹（unit-development folder,UDF）  
  一种非正式文档，其中包括了供开发者在编程期间使用的记录。“单元”没有严格的定义，一般指类，也可指程序包或者文件。UDF的主要用途是提供在其他地方没有说明的设计决策踪迹。很多项目都有标准来指定UDF最少该有什么内容，例如相关需求的复本、某个单元实现的顶层设计的组成部分、开发标准的复本、当前代码清单，以及单元开发者的设计记录。通常仅限于内部使用。
- 详细设计文档  
  低层次的设计文档，描述在类层或者子程序层的设计决定，曾考虑过的其他方案，以及采用所选方案的理由。有时候这些信息含在某个正式文档中，在这种情况下，通常考虑的是将详细设计和构建的过程分开。有时它主要包含收集于UDF的开发者记录；在另一些时候（经常如此），设计细节说明就存在于代码之中。

### 32.2 编程风格作文档
与外部文档相比，内部文档嵌入于程序清单本身，是最详细的文档，位于源码的层次上。由于内部文档与代码的联系最为密切，故也是代码修正后能保持正确的那种文档。
